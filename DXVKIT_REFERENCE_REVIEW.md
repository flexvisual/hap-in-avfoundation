# DXVKit-Plus Reference Review

## Scope and evidence

Reviewed DXVKit-Plus at upstream `main` commit `09f1dbcd4df07774c860b7f42267779b2f7b53ca` on 2026-11-05, primarily its [README and codec table](https://github.com/AmritusG/DXVKit-Plus/blob/09f1dbcd4df07774c860b7f42267779b2f7b53ca/README.md#codec-support), [GPU upload and playback section](https://github.com/AmritusG/DXVKit-Plus/blob/09f1dbcd4df07774c860b7f42267779b2f7b53ca/README.md#getting-frames-onto-the-gpu-030), and published crate descriptions. Performance numbers below are the project's published claims, not measurements reproduced against this Objective-C project.

This is an architectural reference review, not a proposal to adopt DXVKit-Plus's Rust or wgpu implementation. Recommendations are scoped to the existing Objective-C, AVFoundation, and native Metal stack. No source code was changed for this review.

## 1. Features we already implement

### Hap formats and GPU paths

- **Hap R / BC7:** The Hap parser is integrated through the upstream Hap source dependency. `Hap7` is discovered by `AVPlayerItem.hapTrack`; parsed BC7 blocks map to `MTLPixelFormatBC7_RGBAUnorm` and are sampled directly in the normal Metal renderer. The separate RGB-output fallback uses `HapMetalDXTDecoder` to convert BC7 to RGBA on the GPU. See [AVPlayerItemAdditions.m](HapInAVFoundation/AVPlayerItemAdditions.m#L19), [HapMTLPixelBufferTexture.m](HapInAVF%20Test%20App/Metal/HapMTLPixelBufferTexture.m#L67), and [AVPlayerItemHapDXTOutput.m](HapInAVFoundation/AVPlayerItemHapDXTOutput.m#L704).
- **Hap Q / Hap Q Alpha:** Both are reconstructed on the GPU in the Metal fragment shader. Hap Q samples its BC3 YCoCg plane; Hap Q Alpha samples the BC3 YCoCg plane and separate BC4 alpha plane. This is already a good direct-to-render design and avoids an intermediate full-frame RGBA conversion for display. See [HapMTKView.m](HapInAVF%20Test%20App/Metal/HapMTKView.m#L322) and [HapMTKViewShader.metal](HapInAVF%20Test%20App/Metal/HapMTKViewShader.metal#L54).
- **BC6H format mapping:** The test app maps unsigned and signed Hap BC6H texture formats to Metal BC6H texture formats and selects the sampleable shader path for the Hap HDR subtype. This is useful lower-level plumbing, but does not amount to complete Hap HDR playback support; see the gap below. See [HapMTLPixelBufferTexture.m](HapInAVF%20Test%20App/Metal/HapMTLPixelBufferTexture.m#L71) and [HapMTKView.m](HapInAVF%20Test%20App/Metal/HapMTKView.m#L326).

### Existing reuse, asynchronous decode, and seeking

- **GPU texture reuse exists:** The test app pools texture-wrapper objects and reuses their compatible Metal textures. The existing Hap1 performance report measured two wrapper objects and two Metal textures created, with 898 wrapper reuses during its 30-second run. This is not a persistent upload-staging-buffer ring, but it means texture allocation is already amortized in that measured case. See [HapMTLPixelBufferTexture.m](HapInAVF%20Test%20App/Metal/HapMTLPixelBufferTexture.m#L241) and [HAP_METAL_PERFORMANCE.md](HAP_METAL_PERFORMANCE.md#L19).
- **Decode is asynchronous for playback:** `allocFrameClosestToTime:` returns an available/nearby frame without waiting and schedules missing work on a dedicated high-priority serial decode queue. Hap chunk work is parallelized through `dispatch_apply`. A bounded decoded-frame cache is already present. See [AVPlayerItemHapDXTOutput.h](HapInAVFoundation/AVPlayerItemHapDXTOutput.h#L54) and [AVPlayerItemHapDXTOutput.m](HapInAVFoundation/AVPlayerItemHapDXTOutput.m#L72).
- **A synchronous exact-time API and zero-tolerance seek are present:** `allocFrameForTime:` fetches and decodes the requested sample synchronously, and the test harness exercises `AVPlayer` seeks with zero before/after tolerance. These are useful primitives and tests, but are not a frame-indexed transport, step API, or proof of exact-frame behavior across arbitrary seeking and caching. See [AVPlayerItemHapDXTOutput.h](HapInAVFoundation/AVPlayerItemHapDXTOutput.h#L61) and [HapInAVFTestAppDelegate.m](HapInAVF%20Test%20App/HapInAVFTestAppDelegate.m#L173).

## 2. Missing functionality and notable gaps

- **Hap HDR is not reachable through normal `AVPlayerItem` track selection.** `AVAssetTrack.isHapTrack` recognizes `HapH`, but `AVPlayerItem.hapTrack` only switches through `Hap7` and omits `HapH`. The app's format map and renderer do not compensate for that discovery omission. Add a targeted HapH sample and verify track discovery through the actual player path before claiming playback support. See [AVAssetAdditions.m](HapInAVFoundation/AVAssetAdditions.m#L44) and [AVPlayerItemAdditions.m](HapInAVFoundation/AVPlayerItemAdditions.m#L19).
- **Hap HDR lacks a defined RGB/SDR output path.** The RGB-output decode switch has a BC7 compute-conversion case, but no BC6H case; unsupported formats reach its error branch. Direct BC6H sampling is a separate path and requires an explicit color-space, transfer-function, tone-mapping, and display policy. See [AVPlayerItemHapDXTOutput.m](HapInAVFoundation/AVPlayerItemHapDXTOutput.m#L704) and [HapMTLPixelBufferTexture.m](HapInAVF%20Test%20App/Metal/HapMTLPixelBufferTexture.m#L71).
- **The normal Metal upload path does not expose a persistent GPU staging ring or a multi-stage in-flight scheduler.** It calls `replaceRegion:withBytes:` on managed textures and synchronizes them with a blit encoder. The texture objects can be reused, but the code does not own reusable upload buffers or coordinate their lifetime with multiple in-flight uploads. See [HapMTLPixelBufferTexture.m](HapInAVF%20Test%20App/Metal/HapMTLPixelBufferTexture.m#L165) and [HapMTLPixelBufferTexture.m](HapInAVF%20Test%20App/Metal/HapMTLPixelBufferTexture.m#L200).
- **Decode-ahead is limited, not absent.** The closest-frame API schedules work asynchronously and queues requested times, but the Hap decoder itself uses one serial queue; it decodes queued frames in sequence. This differs from a bounded lookahead cache with worker-side decode overlapping a GPU submission pipeline. Chunk parallelism is already present, so do not simply add more per-frame threads without measurement. See [AVPlayerItemHapDXTOutput.m](HapInAVFoundation/AVPlayerItemHapDXTOutput.m#L478) and [AVPlayerItemHapDXTOutput.m](HapInAVFoundation/AVPlayerItemHapDXTOutput.m#L555).
- **Closest-time playback is intentionally not exact-frame delivery.** The playback API may return a cached nearby/previous frame while fetching the requested time asynchronously. The synchronous exact-time API is available for uses such as frame extraction, but can block the caller. There is no public frame-number transport/step facility that establishes frame identity through seeks. See [AVPlayerItemHapDXTOutput.h](HapInAVFoundation/AVPlayerItemHapDXTOutput.h#L54) and [AVPlayerItemHapDXTOutput.m](HapInAVFoundation/AVPlayerItemHapDXTOutput.m#L966).
- **The sample renderer is a single-video playback demonstration, not a multilayer compositor benchmark.** The current report provides strong single-stream Hap1 measurements, but does not establish scaling for many simultaneous layers or contention between decode, uploads, and composition. See [HAP_METAL_PERFORMANCE.md](HAP_METAL_PERFORMANCE.md#L13).

## 3. Potential optimizations

Prioritize by measured need. The existing 30-second Hap1 run reported 29.99 Hap FPS, zero estimated dropped frames, 15.3% of one CPU core, 0.220 ms average CPU time in the compressed-texture upload call, and 0.0542 ms average render GPU execution. That indicates one Hap1 stream is already well within budget; the most plausible gain from DXVKit-Plus's upload pipeline is **multi-layer throughput and reduced scheduling jitter**, not a demonstrated increase to single-stream FPS. See [HAP_METAL_PERFORMANCE.md](HAP_METAL_PERFORMANCE.md#L19) and [HAP_METAL_PERFORMANCE.md](HAP_METAL_PERFORMANCE.md#L36).

| Priority | Candidate improvement | Native implementation direction | Expected benefit and validation |
|---|---|---|---|
| 1 | Persistent upload staging and bounded in-flight uploads | Prototype a small ring of reusable `MTLBuffer` staging slots and completion-tracked upload resources. Encode copies into reusable compressed textures with Metal blit commands; return slots to the ring only after the command buffer completes. Retain the current path as a fallback and check BC block row/alignment requirements. | Can reduce repeated implicit staging/allocation work and CPU/GPU serialization under many layers. DXVKit-Plus reports 16-layer, 1080p HAP throughput rising from 163–202 to 692–939 “steps per second” on its Mac Studio; this is a project-specific result, not a predicted gain for this app. Benchmark this project's upload CPU time, frame latency, and 1/4/8/16-layer dropped frames before adopting. |
| 2 | Explicit decode/upload/present overlap | Preserve the current frame cache, but bound the number of decoded-ahead frames and associate each with exact PTS plus an epoch/generation. Allow the next Hap frame to decode while the prior frame's upload/render is in flight; prevent slot reuse until completion. | Improves worst-case pacing when CPU decompression and transfer compete, especially with several layers. Measure p50/p95/p99 decode-to-present latency and queue depth; avoid unbounded prefetch memory. |
| 3 | Frame-accurate seek and stepping validation | Build tests around sample PTS and frame identity, including shuffled seeks, adjacent-frame stepping, repeated seeks, and seeks that invalidate pending decode/upload work. Keep `CMTime` rational values and use exact tolerances where the caller requires exactness. Do not replace AVFoundation; use the existing exact-time API where appropriate and keep blocking work off the UI/render thread. | Improves deterministic scrubbing and avoids showing a stale nearby cached frame after a seek. DXVKit-Plus documents per-frame identity and shuffled-seek verification; replicate the test discipline with Hap fixtures, not its Rust transport. |
| 4 | Complete Hap HDR as a separately specified feature | First wire `HapH` track discovery. Then define direct BC6H rendering/color handling and separately decide whether an RGB fallback is required. Add unsigned/signed BC6 fixtures and reference frames before implementing conversion. | Converts partial format plumbing into testable playback support. Benefit is format coverage, not an FPS optimization. |
| 5 | Retain direct GPU Hap Q/Q Alpha composition | Continue sampling BC3 YCoCg and BC4 alpha in the fragment shader. Only add an offscreen compute conversion if a concrete consumer needs reusable RGBA output or cross-layer processing; avoid adding an unnecessary full-frame write/read pass to ordinary display. | The current path already avoids RGBA conversion for display. DXVKit-Plus's GPU conversion architecture is useful as a reference for alternate consumers, but does not show that replacing this renderer's direct fragment conversion would be faster. |

DXVKit-Plus's README says its 0.3.0 uploader batches layer uploads in a command encoder, keeps at most two steps in flight, uses persistent staging, and can decode directly into staged memory. Its published HAP layer figures imply approximately 3.4–5.8x throughput across the stated old/new range. Treat this as a testable hypothesis for this project's multi-layer workload: hardware, frame mix, timing method, and meaning of “step” differ, and the figures are not a fair single-layer comparison with our Hap1 FPS measurements.

## 4. Compatibility considerations

- **Stay native.** Use Objective-C/C/C++ and Metal command queues, buffers, textures, and completion handlers. DXVKit-Plus's Rust and wgpu APIs are architectural examples only; neither should become a dependency.
- **Preserve compressed blocks.** BC1, BC3, BC4, BC6H, and BC7 availability/format handling varies with target OS/device. Keep capability checks and the current proven Hap1 path. Do not assume BC6H color/display correctness merely because a Metal texture format is available.
- **Respect ownership and synchronization.** Decoder frame data is allocator-owned and may be recycled. An asynchronous upload must retain or copy the source bytes until GPU work has consumed them. Texture/staging ring reuse must be completion-driven, not based only on display callbacks.
- **Keep exact PTS separate from presentation scheduling.** Seeking and decode-ahead can race with older requested work. Cancel or tag stale work after seeks and validate actual frame identity, not only that playback resumes.
- **Keep Hap-specific work inside HapInAVFoundation.** Continue using the upstream Hap parser and existing framework API. Do not import DXV-specific demuxing, packet handling, or codec behavior into this framework.
- **Evaluate DXV separately as a possible `ModDXV` framework.** DXVKit-Plus claims clean-room DXV1/2/3 decode and provides DXV vectors/architecture to investigate, but its README explicitly says it is independent and unaffiliated with Resolume or Vidvox. Before a separate framework is considered, assess its actual codec coverage, licensing/provenance, format compatibility, test vectors, and API boundary. Do not treat this Hap review as endorsement or integration approval.

## 5. Recommended implementation order

1. **Add Hap HDR discovery and test coverage first, without changing decode/render internals.** Confirm `HapH` selection end-to-end, then document which direct BC6H path is supported and which RGB/display paths are not.
2. **Add frame-identity tests for seeks and cache invalidation.** Use existing APIs and sample PTS. Test exact and shuffled seeks, adjacent frames, repeated seeks, and stale asynchronous completion after a new seek.
3. **Create a native Metal upload benchmark for multiple Hap layers.** Compare current `replaceRegion` uploads against a small persistent staging ring, capturing CPU upload duration, GPU copy duration, memory, p95/p99 frame latency, dropped frames, and scaling by layer count. Do not change the default path until results show a benefit.
4. **If multi-layer measurements justify it, add bounded pipelining.** Overlap decode-ahead with upload/render and bound queues/buffers. Keep existing chunk-parallel decode and the current texture pool; validate single-stream behavior and pause/seek/restart before expanding use.
5. **Leave the Hap Q/Q Alpha fragment conversion unchanged unless a consumer requires RGBA textures.** Establish correctness against reference frames first; avoid introducing an extra conversion pass for ordinary display.
6. **Explore DXV only in a separate ModDXV design/review.** Keep its format parser, demux, licensing review, and APIs outside HapInAVFoundation.
